# Glossary

The definitions below are plain-language introductions.
Individual standards may define the terms more precisely or use them differently.

| Term or acronym | Plain-language meaning |
| --- | --- |
| **ABI — Application Binary Interface** | The rules governing how compiled components interact, including calling conventions and data layout. |
| **AFNOR — Association française de normalisation** | The French organization responsible for coordinating national standardization. |
| **API — Application Programming Interface** | The functions and other interfaces through which software components interact. |
| **ASIL — Automotive Safety Integrity Level** | An ISO 26262 classification assigned to a safety goal based on assessed risk and used to determine the rigor expected from development and verification activities. |
| **Assurance** | Justified confidence, supported by evidence, that software or an activity satisfies defined expectations. |
| **Certification** | Acceptance or approval within a defined regulatory or certification scheme; qualification does not automatically constitute certification, and vice versa. |
| **CI — Continuous Integration** | The practice of regularly combining changes and running automated checks on them. |
| **CIA — Change Impact Analysis** | An assessment of how a change may affect a tool, its intended use, or its qualification evidence, including relevant operational-environment changes in the DO-330 context. |
| **COTS — Commercial Off-The-Shelf** | A commercially available product acquired for use without developing it specifically for the purchasing project. |
| **CUSWT — Confidence in the Usage of Software Tools** | Confidence, supported by appropriate evidence and controls, that a software tool is suitable for its specified use. |
| **DO — RTCA document designation** | A prefix used in the identifiers of RTCA documents, such as DO-178C and DO-330. |
| **Downstream user** | An organization or project that selects, configures, and integrates LLVM components into its own product or development process. |
| **E/E/PE — Electrical / Electronic / Programmable Electronic** | A description of the types of systems addressed by IEC 61508. |
| **EASA — European Union Aviation Safety Agency** | The European Union agency responsible for civil aviation safety. |
| **ED — EUROCAE document designation** | A prefix used in the identifiers of EUROCAE documents, such as ED-12C and ED-215. |
| **ELISA — Enabling Linux in Safety Applications** | A project developing shared approaches to the use of Linux in safety-critical applications. |
| **EN — European Standard** | A designation for a standard adopted at the European level, such as EN 50716. |
| **EUROCAE — European Organisation for Civil Aviation Equipment** | An organization that develops standards and guidance for civil aviation equipment. |
| **Evidence** | Reviewable information such as requirements, source references, design descriptions, review records, tests, results, coverage, and anomaly reports. |
| **FAA — Federal Aviation Administration** | The United States agency responsible for civil aviation oversight. |
| **FAS — Forum for Aeronautical Software** | A forum that discusses aeronautical software topics and publishes informational topic papers. |
| **FDA — Food and Drug Administration** | The United States agency that regulates medical devices, among other products. |
| **FMEA — Failure Modes and Effects Analysis** | A systematic analysis of ways an item or process could fail and the effects of those failures. |
| **FTP — FAS Topic Paper** | An informational paper published by the Forum for Aeronautical Software on a specific topic. |
| **Functional safety** | Safety that depends on an electrical, electronic, or programmable system behaving correctly in response to its inputs and failures. |
| **ID — Identifier** | A label used to distinguish and reference a particular record, item, or use case. |
| **IEC — International Electrotechnical Commission** | An organization that develops international electrotechnical standards, including IEC 61508 and IEC 62304. |
| **ISO — International Organization for Standardization** | An organization that develops international standards, including ISO 26262. |
| **MC/DC — Modified Condition/Decision Coverage** | A structural-coverage criterion that shows the independent effect of each condition on a decision’s outcome. |
| **NF — Norme française** | A prefix identifying a French standard or French adoption of another standard, as in NF EN 50716. |
| **OpenSSF — Open Source Security Foundation** | An organization coordinating work to improve the security of open-source software. |
| **OSS — Open Source Software** | Software whose source code is available under a license that permits use, study, modification, and redistribution under stated conditions. |
| **QE — Qualification Evidence** | An identifier for an evidence item referenced by TPL-004. |
| **QF — Qualification Finding** | An identifier for a finding recorded in TPL-004. |
| **QMA — Qualification Method or Activity** | An identifier for a qualification method or activity recorded in TPL-004. |
| **QMS — Quality Management System** | An organization’s processes for managing and demonstrating the quality of its products or services. |
| **QMSR — Quality Management System Regulation** | FDA requirements for the quality management systems of medical-device manufacturers. |
| **Qualification** | An assessment, supported by evidence, that a component or tool is suitable for a defined use under stated conditions; its formal meaning and required activities vary among standards. |
| **RAMS — Reliability, Availability, Maintainability and Safety** | A lifecycle-oriented way of considering four related system properties together, particularly established in railway engineering; the properties influence one another, but high reliability or availability alone does not demonstrate safety. |
| **RTCA — Radio Technical Commission for Aeronautics** | An organization that develops aviation consensus standards, including DO-178C and DO-330. |
| **Safety-related software** | Software whose correct or incorrect behavior can contribute to preventing, controlling, or causing an unsafe situation. |
| **SIL — Safety Integrity Level** | A classification used by IEC 61508 and some related standards to express the required level of risk reduction and associated rigor; its detailed meaning is standard-specific. |
| **SOUP — Software of Unknown Provenance** | IEC 62304 terminology for certain existing software for which adequate development-process records may not be available; it does not mean that the software is necessarily unsafe. |
| **SQA — Software Quality Assurance** | Activities that provide confidence that software work follows its defined processes and quality requirements. |
| **Structural coverage** | Information showing which parts of the implementation, such as statements or branches, were exercised by tests. |
| **SW — Software** | A short form used in document titles and descriptions for software. |
| **T1/T2/T3 — Tool classification labels** | Labels used by IEC 61508 and EN 50716 to classify tools; each standard’s own definitions apply. |
| **TCL — Tool Confidence Level** | An ISO 26262 classification derived from tool impact and tool error detection that helps determine qualification expectations. |
| **TD — Tool Error Detection** | An ISO 26262 classification concerning confidence that errors arising from a tool will be prevented or detected. |
| **Threat model** | A structured description of relevant assets, assumptions, trust boundaries, threats, vulnerabilities, responsibilities, and controls from a security perspective. |
| **TI — Tool Impact** | An ISO 26262 classification concerning whether a tool malfunction could introduce errors or fail to detect them. |
| **TOR — Tool Operational Requirements** | DO-330 requirements describing what a tool must do in its intended operational use. |
| **TPL — Template** | An identifier used for a Qualification Working Group template, such as TPL-004. |
| **TQL — Tool Qualification Level** | A level used with DO-178C and DO-330 to determine the applicable tool-qualification objectives. |
| **Traceability** | Explicit, maintainable links between related information, such as a required behavior and the tests intended to verify it. |
| **UC — Use Case** | A description of a particular way a component or tool is intended to be used. |
| **Upstream** | The LLVM community and repositories where shared components are developed and reviewed. |
| **Validation** | Checking that the resulting system or software is suitable for its intended use in its actual or representative environment. |
| **Verification** | Checking that an artifact or implementation satisfies its specified requirements or other defined criteria. |
